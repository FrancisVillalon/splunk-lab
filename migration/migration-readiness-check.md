#splunk #migration

# Summary
This document decides whether the environment is ready to be migrated, before any work starts. The question that should be answered here is “Do we understand this system well enough to attempt the move, and do we have an idea of the target design?”.

This document confirms the existing system is fully documented, that the important knowledge objects related to a scenario living on it are accounted for in a manifest, and that a target container design exists.
# Scope
This migration moves the existing Splunk instance from the Ubuntu VM onto Docker on localhost. It is a state move only. The version, configuration and data are all the same, just running in a different environment.

|                | Source (VM)                           | Target (Container)       |
| -------------- | ------------------------------------- | ------------------------ |
| Host           | Ubuntu Server 22.04.5, `172.16.58.10` | Docker 29.7.2, localhost |
| Splunk version | 10.4.2                                | 10.4.2                   |

The only scenario that exists in the current Splunk instance is GlobalCart, and as such it will be the only scenario affected by this migration. The apps and data related to LumeoStreaming and IronvaleFinancial will be added after the environment has been migrated based on the documentation relating to these scenarios.

# Target Design
The following outline the design decisions/considerations that have to be made.

| Decision                    | Answer                                                                                                                                                                                      | Reason / Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Splunk Version              | The docker container will have splunk version 10.4.2                                                                                                                                        | The Splunk Version of the target system should be the same as the source system.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Volume layout               | Named volumes will be created for `$SPLUNK_HOME/etc` and `$SPLUNK_HOME/var`. The data for these volumes will be obtained from the VM in its last known good state and not altered.          | This is required for data persistence on the docker container. The usage of named volumes over a bind mount is detailed in the [Splunk documentation](https://splunk.github.io/docker-splunk/STORAGE_OPTIONS.html).                                                                                                                                                                                                                                                                                                                                                                                                  |
| Provisioning method         | `user-seed.conf` will not be used in the docker container as the `passwd` file already exists. Instead the ansible env vars will be used.                                                   | The ansible playbook requires an admin user's credentials to either be created or available to it to create the splunk environment. <br><br>Given that we are essentially rebuilding an already existing environment, we will provide the password to the default admin account that existed on the old system.<br><br>In the event that this account does not exist, we can backup and then delete the current passwd file, provide it a user-seed.conf and it will recreate a new passwd using the existing splunk secret. <br><br>Then all we have to do is append our existing passwd entries into the new file. |
| Published ports             | Only 8000 and 8089 ports will be published as all data lives in `csv` files.                                                                                                                | No forwarders exist in this deployment and all data is stored in `csv`. Therefore, only the ports for the management api (8089) and the web interface (8000) should be published.                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Shutdown/ Restart mechanism | Stop the splunk instance through the splunk cli tool in the container then do a docker compose down.                                                                                        | Docker compose down has a short grace period before it sends a SIGKILL. Meaning it is possible that it forces a shutdown while Splunk is writing data.<br><br>This is in contrast to systemctl which handles it more gracefully due to how the splunk unit file is defined.                                                                                                                                                                                                                                                                                                                                          |
| Resource limits             | Docker container will be limited to 8GB and 2 CPU cores. Unlike the VM no disk usage constraints are enforced.                                                                              | RAM and CPU constraints remain the same because the purpose and load of the deployment remains the same. <br><br>No disk usage constraint is because instead of a virtual disk being created for the instance, the data instead lives on the host disk. To limit the size of data, the use of a stanza to limit the max index size of a given index is more appropriate.                                                                                                                                                                                                                                             |
| License delivery            | `$SPLUNK_HOME/etc` contains the required licenses. Therefore, container immediately receives the license with the named volume. The license used is the same developer license the VM uses. | In event this fails, a copy of the license file exists that can then be uploaded through the GUI                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| KV store migration method   | KV store directory will be excluded from the `$SPLUNK_HOME/var` tarball. The kv store will be restored on the new splunk instance as a post-start step.                                     | This is to avoid issues with mismatching mongodb versions. Even though in this case the mongo versions match, it is better to just do the documented and supported way of migrating a kvstore instead of creating a failure point by copy-pasting the entire data. [Reference](https://help.splunk.com/en/splunk-enterprise/administer/admin-manual/9.2/administer-the-app-key-value-store/back-up-and-restore-kv-store#prepare-to-restore-the-kv-store-data-1)                                                                                                                                                      |
| Networking                  | The Splunk instance will only be reachable on `127.0.0.1` and this will be defined in `docker-compose.yml`.                                                                                 | The splunk instance is only used for scenario testing that happens entirely on localhost. Running the splunk instance on a local docker container means we can just assign the instance to our loopback address.                                                                                                                                                                                                                                                                                                                                                                                                     |

# Risk register
Table of risks, their signal and the response

| Risk                                                                                                                                                    | Signal                                                                                                                                                                                                                                                                                                                              | Response                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| KV store comes back empty or fails the restore                                                                                                          | kvstore/status is not healthy, or there are collections but they are all empty                                                                                                                                                                                                                                                      | Re-run the restore from backup. If kvstore fails, recreate completely using csv backup                 |
| UID/GID mismatch. The persistent folders `var` and `etc` may be owned by a user under a UID/GID that is different from what is being used in the image. | Splunkd will not start due to permission errors when trying to access `$SPLUNK_HOME/etc` and `$SPLUNK_HOME/var`                                                                                                                                                                                                                     | Fix permission inside the container as a post-extract step.                                            |
| Container start generates a new `splunk.secret` instead of using the mounted one                                                                        | `splunk.secret` in the container has a checksum different from our known checksum of the original `splunk.secret`. <br><br>`splunk.secret` is a long randomly generated string that is used to encrypt secrets in the splunk app. If the container generates a new one, it will be unable to decrypt the existing encrypted secrets | Confirm that `etc/splunk.secret` is identical after first start; restore from `etc` backup if replaced |
